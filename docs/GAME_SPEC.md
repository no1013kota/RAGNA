# RAGNA Online ギルド・ギルドバトル仕様書

## 1. この文書について

この文書は、RAGNA Discord Botへ追加するゲーム機能「RAGNA Online」の正式な設計基準です。
元のアイデアメモに含まれていた具体的な数値、画面例、戦闘ルールを残しながら、実装・確認・運用がしやすい形に整理しています。

- 文書ステータス：設計中
- 対象範囲：ギルド、使い魔、ギルドバトル
- 対象外：既存の評価、宿屋、問い合わせなどの仕様変更
- 未確定事項：本文中に `【決定必要】` と記載

この文書に書かれていない挙動を実装時の判断だけで決めず、重要な仕様は追記してから実装します。

## 2. 開発方針

ゲーム機能は次の4段階に分けて公開します。

1. ギルド設立・参加・脱退・管理
2. 使い魔の所有・確認・バトル編成
3. 通常攻撃を中心とした基本ギルドバトル
4. アクティブスキル・パッシブスキル

ギルド機能が安定するまでは、ギルドバトルを本番公開しません。各段階でDiscord上の動作確認と自動テストを完了してから次へ進みます。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| プレイヤー | RAGNA Onlineを利用するDiscordメンバー |
| ギルド | プレイヤーが所属する常設組織 |
| ギルドマスター | ギルドの設立者またはマスター権限を譲り受けたプレイヤー |
| 出場者 | ギルドバトルへ参加する最大5人のギルドメンバー |
| 使い魔マスター | 使い魔の名前、基本能力、画像などの共通定義 |
| 所有使い魔 | プレイヤーが実際に所有する使い魔。レベルなどの個別情報を持つ |
| 戦闘用使い魔 | バトル開始時に所有使い魔から作る一時的なコピー |
| Battle Engine | Discord表示から独立して戦闘ルールを処理する仕組み |
| TC | Discordのテキストチャンネル |
| VC | Discordのボイスチャンネル |

## 4. 既存RAGNA Botとの対応

- 「騎士」は現在の `ROLE_MEMBER` に対応します。
- 「七星」は現在の `ROLE_SUB_MANAGER` に対応します。
- ギルド料金は既存のcoin残高から支払います。
- プレイヤーランクの参照先として、既存DBのクラス情報が候補になります。
- 【決定必要】ギルドを設立できるのは騎士ロールの所有者だけか、七星など上位の運営ロールも含めるか。
- 【決定必要】プレイヤーランクの正式な参照元を `members.class` に統一するか。

## 5. ギルド基本仕様

### 5.1 所属ルール

- 1プレイヤーが同時に所属できるギルドは1つです。
- ギルド設立者は自動的にギルドマスターになります。
- ギルドマスターもギルド人数の1人として数えます。
- 初期定員は5人です。
- メンバー枠は1枠100,000 coinで拡張できます。
- 【決定必要】1ギルドの最大人数。
- 【決定必要】サーバー全体で作成できるギルド数の上限。

### 5.2 ギルド設立

- 設立費用は1,000,000 coinです。
- 既にギルドへ所属しているプレイヤーは設立できません。
- 残高不足の場合、ギルドやDiscordチャンネルは作成しません。
- 残高確認、費用の減算、取引履歴、ギルド登録は可能な限り一体の処理として扱います。
- Discordカテゴリーまたはチャンネルの作成に失敗した場合、途中状態を残さず、支払ったcoinを返金します。
- 【決定必要】ギルド名の最小・最大文字数。
- 【決定必要】同名ギルドを許可するか。
- 【決定必要】ギルド名に使用できない文字・単語・メンション表現。
- 【決定必要】ギルド名を後から変更できるか。変更できる場合の費用と回数制限。

### 5.3 ギルド専用カテゴリー

設立時に次のDiscordカテゴリーとチャンネルを自動作成します。

```text
【ギルド名】
├─ ギルドTC
├─ ギルドVC
├─ ギルドマスター専用TC
├─ バトル出場者専用TC
└─ バトルcommand
```

各チャンネルの用途は次のとおりです。

| チャンネル | 用途 |
| --- | --- |
| ギルドTC | ギルドメンバーの日常会話 |
| ギルドVC | ギルドメンバーの通話 |
| ギルドマスター専用TC | 参加申請、ギルド管理、バトル管理 |
| バトル出場者専用TC | 出場者への連絡と使い魔セット |
| バトルcommand | 戦闘中の攻撃・スキル操作 |

基本権限は次のとおりです。

- ギルドTC・VC：所属メンバーだけが閲覧・利用できます。
- ギルドマスター専用TC：ギルドマスターだけが閲覧・操作できます。
- バトル出場者専用TC：現在セットされている出場者とギルドマスターが閲覧できます。
- バトルcommand：通常時は待機表示とし、戦闘中だけ有効な操作を表示します。
- Botはすべてのチャンネルを閲覧・管理できます。
- 出場者セットを変更した場合、専用TCの閲覧権限を自動更新します。
- 【決定必要】ギルドカテゴリーを作成する親カテゴリや並び順。
- 【決定必要】ギルドマスター以外の運営がすべてのギルドチャンネルを閲覧できるか。
- 【決定必要】ギルド解散後にチャンネルを即時削除するか、一定期間アーカイブするか。

カテゴリーID、各チャンネルID、作成状態はDBへ保存し、Bot再起動後も利用できるようにします。

## 6. ギルド検索・参加申請

### 6.1 ギルド検索パネル

ギルド未所属プレイヤーは、常設のギルド検索パネルからギルドを選び、参加申請できます。

- 表示候補にはギルド名、現在人数、定員を含めます。
- 満員のギルドには申請できません。
- 自分が既に所属している場合は新規申請できません。
- パネルには常時「ギルド脱退」操作も設置します。
- 【決定必要】ギルドの説明文、アイコン、募集状態を持たせるか。
- 【決定必要】検索の並び順。候補は設立順、人数順、名前順など。

### 6.2 通常の参加申請

申請すると、対象ギルドのギルドマスター専用TCへ次のようなEmbedを投稿します。

```text
【ギルド参加申請】

申請者
@Player

[承認] [拒否]
```

- 承認すると、申請者をギルドメンバーとして登録し、ギルドチャンネルの権限を付与します。
- 拒否すると、ギルドへの加入は行いません。
- 回答済みの申請Embedは削除します。
- マスター専用TCには原則として未処理の申請だけを残します。
- 承認時にも定員と所属状態を再確認します。
- 承認と拒否のボタンは、対象ギルドの現在のマスターだけが操作できます。
- 【決定必要】申請者へ承認・拒否結果をDMで通知するか、操作したチャンネルだけに通知するか。
- 【決定必要】参加申請の有効期限。
- 【決定必要】同じプレイヤーが複数ギルドへ同時申請できるか。
- 【決定必要】拒否後に再申請できるまでの待機時間。

### 6.3 満員時

申請を作る前に、次を判定します。

```text
現在人数 >= ギルド定員
```

満員なら申請者だけへ次の内容を表示します。

> このギルドは現在満員のため参加申請できません。

この場合、ギルドマスターには通知せず、DBにも有効な申請を作りません。

## 7. 脱退・追放・譲渡・解散

### 7.1 一般メンバーの脱退

- 一般メンバーはギルド検索パネルの「ギルド脱退」から自分で脱退できます。
- 脱退するとギルド専用チャンネルの閲覧権限を失います。
- 出場者にセットされていた場合は出場者セットからも解除します。
- 【決定必要】バトル進行中の出場者による脱退を禁止するか。
- 【決定必要】バトル申請中・募集中・編成ロック中の脱退を許可するか。
- 【決定必要】脱退後に別ギルドへ加入できるまでの待機時間。

### 7.2 メンバー追放

- ギルドマスターは所属する一般メンバーを追放できます。
- 追放後はギルド専用チャンネルの権限を解除します。
- 出場者にセットされていた場合は出場者セットからも解除します。
- マスター自身は追放対象にできません。
- 【決定必要】追放理由の入力、対象者への通知、再加入までの待機時間。

### 7.3 マスター譲渡

- ギルドマスターは所属メンバー1人へマスター権限を譲渡できます。
- 譲渡先は現在そのギルドへ所属しているプレイヤーに限ります。
- 譲渡後、旧マスターは一般メンバーになります。
- ギルドマスター専用TCの閲覧権限を同時に切り替えます。
- マスターは直接脱退できません。譲渡後に一般メンバーとして脱退するか、ギルドを解散します。
- 【決定必要】誤操作防止のため、譲渡先本人の承認を必要とするか。

### 7.4 メンバー枠拡張

- 1枠につき100,000 coinを支払います。
- 操作できるのはギルドマスターです。
- 残高不足の場合は拡張しません。
- coin減算と定員更新は一体のDB処理として扱います。
- 【決定必要】拡張費用をマスター個人残高から支払うか、ギルド共有資金を作るか。
- 【決定必要】最大定員。

### 7.5 ギルド解散

- ギルドマスターだけが実行できます。
- 誤操作を防ぐ確認画面を表示します。
- バトル進行中は解散できません。
- 所属メンバー全員の所属状態とチャンネル権限を解除します。
- 未処理の参加申請、バトル申請、バトル募集を終了します。
- 【決定必要】設立費用・枠拡張費用を返金するか。基本案は返金なしです。
- 【決定必要】戦績と過去ログを残すか、ギルド情報と一緒に削除するか。
- 【決定必要】Discordカテゴリーを即時削除するか、運営確認後に削除するか。

## 8. ギルドマスター用パネル

ギルドマスター専用TCへ、次の2つの常設パネルを置きます。

### 8.1 ギルド管理

```text
[メンバー追放]
[ギルド解散]
[マスター譲渡]
[メンバー枠拡張]
```

### 8.2 ギルドバトル

```text
[メンバーセット]
[セット確認]
[バトル申請]
[バトル募集]
```

常設ボタンには固定の `custom_id` を設定し、RailwayやBotの再起動後にも操作できるようにします。

## 9. バトル出場者セット

- ギルドマスターが、所属メンバーから最大5人を選択します。
- 正式な5対5バトルを開始するには、両ギルドとも5人必要です。
- 選択されたメンバーには、バトル出場者専用TCの閲覧権限を付与します。
- セットを変更した場合、追加された人へ権限を付与し、外れた人から権限を削除します。
- 同じプレイヤーを重複して選択できません。
- 他ギルドのプレイヤーを選択できません。
- バトルの編成がロックされた後はセットを変更できません。
- 【決定必要】5人未満のカジュアルバトルを将来許可するか。本仕様の正式戦は5対5です。

## 10. 使い魔

### 10.1 データの分離

使い魔は次の3種類のデータに分けます。

1. 使い魔マスター：名前、ランク、基本HP、基本ATK、行動順、性別、画像、スキル
2. 所有使い魔：所有者、使い魔ID、レベルなどプレイヤー固有の情報
3. 戦闘用使い魔：バトル開始時点の能力値と一時的なHP・効果

バトル中のダメージで所有使い魔の永続データを直接変更しません。

### 10.2 使い魔セット

- 出場者専用TCから、各出場者が自分の所有使い魔を1体選択します。
- 所有していない使い魔は選択できません。
- 出場者セットから外れた場合、使い魔セットも解除します。
- バトル開始直前に、現在も所有しているか再確認します。
- バトル終了後は、両ギルド5人全員の使い魔セットを自動解除します。
- 次のバトルでは改めて使い魔を選択しなければなりません。

### 10.3 使役可能ランク

通常プレイヤーは、自分のランクより1段階上までの使い魔を使用できます。

| プレイヤーランク | 使用可能な使い魔ランク |
| --- | --- |
| B | C・B・A |
| A | C・B・A・S |
| S | C・B・A・S |

七星は特権として、プレイヤーランクに関係なくC～Sのすべてを使用できます。Bランクの七星もSランク使い魔を使用できます。

```text
七星か？
├─ YES → C～Sすべて使用可能
└─ NO  → 自分のランクより1段階上まで
```

- 【決定必要】Cランクのプレイヤーが使用できる使い魔ランク。候補はC・Bです。
- 【決定必要】プレイヤーにクラス情報がない場合の扱い。
- 【決定必要】使い魔ランクの将来的な追加を許可するか。

### 10.4 所有・成長

- 【決定必要】プレイヤーが使い魔を入手する方法。
- 【決定必要】同じ種類の使い魔を複数体所有できるか。
- 【決定必要】使い魔レベルの上限とレベルアップ方法。
- 【決定必要】レベルによるHP・ATK・行動順の変化。
- 【決定必要】使い魔の譲渡、売却、削除を許可するか。
- 【決定必要】初期配布する使い魔と対象プレイヤー。

## 11. 編成確認

ギルドマスターは出場者と使い魔のセット状況を確認できます。

```text
【ギルドバトル編成】

① @PlayerA
使い魔：ロキ Lv.0
準備：✅

② @PlayerB
使い魔：フェンリル Lv.2
準備：✅

③ @PlayerC
使い魔：ガルム Lv.4
準備：✅

④ @PlayerD
使い魔：未設定
準備：❌

⑤ @PlayerE
使い魔：ニーズヘッグ Lv.0
準備：✅
```

準備完了となる条件は次の両方です。

1. 出場メンバーに選ばれている
2. 使用する使い魔をセット済み

出場者に選ばれていても、使い魔が未設定なら準備状態は `❌` です。

## 12. 対戦成立方法

### 12.1 特定ギルドへのバトル申請

- ギルドマスターが対戦したいギルドを指定します。
- 相手ギルドのギルドマスター専用TCへ申請を送ります。
- 相手マスターは承認または拒否できます。
- 承認時に両ギルドの準備状況を確認し、問題がなければ対戦を成立させます。
- 回答済みの申請パネルは無効化または削除します。
- 【決定必要】バトル申請の有効期限。
- 【決定必要】同じギルドが複数の申請を同時に送受信できるか。基本案は1件だけです。
- 【決定必要】申請後に編成を変更できるか。基本案は承認・開始前まで変更可能です。

### 12.2 公開バトル募集

ギルドマスターが「バトル募集」を押すと、ギルドバトル募集チャンネルへ次のようなEmbedを投稿します。

```text
⚔ GUILD BATTLE

「VALHALLA」が対戦ギルドを募集しています。

出場人数：5人
状態：対戦相手募集中

[対戦申請]
```

- 他ギルドのマスターが「対戦申請」から申し込めます。
- 自分のギルドへは申し込めません。
- 対戦成立後は募集を終了し、Embedを「募集終了」へ更新または削除します。
- 【決定必要】募集Embedを更新して残すか、成立後に削除するか。
- 【決定必要】募集の有効期限と、マスターが手動で取り消せるか。
- 【決定必要】複数ギルドから申込みが来た場合、募集側が相手を選べるか、最初の1件で確定するか。

## 13. バトル開始前チェック

対戦が承認されても、即座には戦闘を開始しません。両ギルドについて次を最終確認します。

- 出場者がちょうど5人いる
- 5人全員が使い魔をセットしている
- セットした使い魔を現在も所有している
- プレイヤーが使役条件を満たしている
- 出場者が現在も対象ギルドへ所属している
- 出場者が他の進行中バトルへ参加していない
- ギルドが他の進行中バトルへ参加していない
- ギルドと各チャンネルが利用可能な状態である

すべて通過した場合に次を実行します。

1. 両ギルドの編成をロックする
2. Battleデータを作成する
3. 10体の戦闘用使い魔を作成する
4. 両ギルドの募集・他の申請を終了する
5. 最初の行動者を決定する

途中で条件を満たさなくなった場合は、バトルを開始せず、両ギルドへ不足内容を具体的に通知します。

## 14. 戦闘用使い魔データ

戦闘用使い魔には最低限、次を保存します。

```text
battle_unit_id
battle_id
guild_id
player_id
familiar_instance_id
familiar_id

level
max_hp
current_hp
base_atk
current_atk
action_order
gender

active_skill_used
alive
```

必要に応じて、現在の行動不能状態、最後に処理したターン、スキル発動履歴なども持たせます。

- 所有使い魔のHPと戦闘中のHPは完全に分離します。
- バトル開始後に所有使い魔が成長しても、進行中バトルの能力値は変えません。
- 【決定必要】バトル開始時にランダム補正を加えるか。本仕様の基本案は補正なしです。

## 15. 行動順

- 両ギルドの戦闘用使い魔10体を `action_order` の小さい順に並べます。
- 1番から10番まで進行し、決着していなければ再び1番へ戻ります。
- 戦闘不能の使い魔は自動スキップします。
- 行動不能の使い魔は自動スキップします。
- 自動スキップではギルド持ち時間を消費しません。
- 【決定必要】同じ `action_order` の使い魔がいる場合の優先順位。候補は抽選、登録順、固定の副能力値です。
- 【決定必要】行動順を変化させるスキルを将来許可するか。

## 16. バトルcommandチャンネル

各ギルドの `バトルcommand` が実際の操作場所です。

- 通常時は操作不能またはバトル待機状態にします。
- 自分のギルドの使い魔のターンになると、その使い魔の所有プレイヤーをメンションします。
- 操作できるのは現在の行動者本人です。
- 他の出場者、相手ギルド、第三者による操作は拒否します。

```text
@PlayerA
ロキの行動順です。

[特殊スキル] [攻撃]
```

次のプレイヤーへ移るときは、前回のターン通知メッセージを削除し、新しい行動者をメンションします。commandチャンネルには常に現在の操作対象だけが分かる状態を維持します。

ボタンの二重押しや通信の再送が発生しても、同じ行動を2回処理しないようにします。

## 17. プレイヤーターン

基本的な進行は次のとおりです。

1. ターン開始
2. パッシブスキルのターン開始判定
3. 必要ならアクティブスキルを使用
4. 攻撃を選択
5. 対象を選択
6. ダメージ処理
7. 戦闘不能判定
8. 行動終了
9. 効果の残りターン更新
10. 次の行動者へ移動

アクティブスキルは原則として攻撃前に使用します。アクティブスキルを使っただけでターンを終了せず、その後に通常攻撃を行うのが基本です。

- 【決定必要】スキルによっては攻撃せずターン終了となるものを許可するか。
- 【決定必要】攻撃対象を選ばないまま持ち時間が0になった場合以外に、自動攻撃を行う仕組みを設けるか。

## 18. 戦闘ルール

### 18.1 通常攻撃

- DEFは存在しません。
- 基本ダメージは攻撃者の現在ATKです。
- 現在ATKが8なら8ダメージです。
- ダメージにより `current_hp` を減らします。
- `current_hp <= 0` になった使い魔は戦闘不能です。
- 【決定必要】ATKがデバフで0未満になった場合の最低ダメージ。候補は0または1です。

### 18.2 クリティカル

- 通常攻撃には非常に低い確率でクリティカルが発生します。
- クリティカルダメージは通常ダメージの1.5倍です。
- 各攻撃ごとに独立して判定します。
- 発生率はコードへ直接書かず、設定値として管理します。
- 【決定必要】クリティカル率。
- 【決定必要】1.5倍した結果の端数処理。切り捨て、四捨五入、切り上げのいずれか。
- 【決定必要】スキル攻撃にもクリティカルを許可するか。現仕様では通常攻撃のみです。

### 18.3 回復

- 回復スキルは自分または味方を対象にできます。
- `current_hp` は `max_hp` を超えません。
- 戦闘不能の使い魔は、蘇生効果が明示されていない通常回復では対象にできません。

### 18.4 2回攻撃

- `ATK × 2` の一括ダメージではありません。
- 通常の攻撃処理を2回実行します。
- 各攻撃でクリティカルや攻撃連動効果を個別に判定します。
- 1回目で対象が戦闘不能になった場合の2回目の対象については別途ルールを定めます。
- 【決定必要】1回目で対象が戦闘不能になった場合、2回目を無効にするか、別対象を選ぶか。

### 18.5 戦闘不能と蘇生への備え

- `current_hp <= 0` で戦闘不能になります。
- 戦闘不能になっても、その時点で残っているバフ・デバフ情報は保持します。
- 将来蘇生した場合は、残り効果を引き継ぎます。
- 現段階では蘇生スキル自体は必須実装に含めません。

## 19. 特殊スキル

### 19.1 共通データ

スキルは最低限、次の情報を持ちます。

```text
skill_id
name
description
skill_type
trigger
target_type
effect_type
effect_value
duration_turns
```

`skill_type` は `active` または `passive` です。

- 【決定必要】各スキルの具体的なデータ形式。最初のスキル一覧を基に確定します。

### 19.2 アクティブスキル

プレイヤーが任意にボタンを押して使用します。候補となる効果は次のとおりです。

- 回復
- 魅了
- ATKバフ
- ATKデバフ
- 2回攻撃
- 行動不能
- 状態異常解除

原則として、1体の使い魔につき1バトル1回使用できます。使用済み状態は戦闘用使い魔に保存します。

- 【決定必要】使い魔1体が複数のアクティブスキルを持てるか。
- 【決定必要】「1バトル1回」をスキル単位にするか、使い魔全体で1回にするか。
- 【決定必要】対象選択後のキャンセルを許可するか。

### 19.3 パッシブスキル

プレイヤーは操作せず、Battle Engineが発動条件を満たしたときに自動処理します。

想定例：

- HP50%以下になるとATK+2
- バトル開始時に味方全体ATK+1
- 自分が攻撃を受けたときに発動
- 特定の使い魔と同時出場するとATK+2
- 戦闘不能になる直前に発動
- 常時発動

想定する発動タイミング：

```text
battle_start
turn_start
before_action
before_attack
after_attack
on_damage
hp_threshold
turn_end
on_defeat
always
```

- 同じイベント中に同じパッシブが無限発動しないよう、発動履歴または回数制限を持たせます。
- 発動したパッシブは行動ログへ記録します。
- 【決定必要】各パッシブの1ターン・1バトルあたりの発動回数制限。
- 【決定必要】複数パッシブが同時発動する場合の解決順。

## 20. バフ・デバフ・状態異常

- 能力変化は割合ではなく固定値です。
- 例：`ATK +3`、`ATK -2`。
- 同じ効果を重ね掛けできます。
- 残りターン数は、効果を受けている使い魔自身の行動終了時に1減らします。
- 残りターンが0になった効果は解除します。
- 効果ごとに発生元、値、残りターンを保存します。
- 【決定必要】バフ・デバフの上限値および最大重複数。
- 【決定必要】行動不能で自動スキップした場合も残りターンを減らすか。基本案は減らします。

## 21. 魅了・性別

人型使い魔には性別情報を設定し、内部値は次を基本とします。

```text
male
female
none
```

魅了は「異性の場合のみ行動不能」などの条件判定に利用します。

- 【決定必要】`none` の使い魔は魅了を受けない扱いにするか。
- 【決定必要】性別条件を持たない魅了・行動不能スキルも存在できるか。

## 22. ギルド持ち時間

- 各ギルドはバトル開始時に1時間の持ち時間を持ちます。
- 自ギルドのプレイヤーが操作できる状態の間だけ減少します。
- 相手ギルドのターン中は停止します。
- 行動不能による自動スキップでは消費しません。
- 0になったギルドは時間切れで敗北します。
- 残り時間はDBへ保存し、Discord表示へ反映します。
- 【決定必要】Bot・Railway再起動中の時間を持ち時間から減らすか。基本案は減らさず、復旧後に再開です。
- 【決定必要】1時間とは別に、1操作あたりの短い制限時間を設けるか。

## 23. 行動ログEmbed

行動ログはEmbed形式で投稿し、行動した使い魔の画像をサムネイル表示します。

通常攻撃の例：

```text
⚔ ロキの攻撃                    [ロキ画像]

使用者
@PlayerA

対象
フェンリル

DAMAGE
8

HP
30 → 22
```

クリティカルの例：

```text
⚡ CRITICAL
12 DAMAGE
```

アクティブスキルの例：

```text
✦ SKILL「魅了」

対象：○○
効果：行動不能
残り：2ターン
```

パッシブスキルの例：

```text
✦ PASSIVE SKILL

ロキ「○○」発動
ATK +2
```

- 【決定必要】行動ログを両ギルドの各チャンネルへ投稿するか、共通観戦チャンネルを作るか。
- 【決定必要】過去ログの保存期間と、バトル終了後の閲覧範囲。

## 24. 戦況Embed

各行動終了後に、その時点の戦況をEmbedで表示します。

- 行動ログ：今回何が起きたか
- 戦況Embed：その結果、現在どうなっているか

両ギルド5体について次を表示します。

- 使い魔名
- HPバー
- 現在HP / 最大HP
- 現在ATK
- 戦闘不能状態
- バフ
- デバフ
- 状態異常
- アクティブスキル使用状況

- 【決定必要】戦況Embedを行動ごとに新規投稿するか、最新の1件を更新するか。基本案は最新の1件を更新します。

- 【決定必要】HPバーの文字数と表示記号。
- 【決定必要】相手側に非公開とする能力・スキル情報があるか。基本案はすべて公開です。

## 25. Battle Engine

Battle EngineはDiscordのボタンやEmbedから分離し、入力された戦闘状態と行動から次の状態を計算します。

基本イベント順：

```text
BATTLE_START
↓
TURN_START
↓
BEFORE_ACTION
↓
SKILL
↓
BEFORE_ATTACK
↓
ATTACK
↓
DAMAGE
↓
AFTER_ATTACK
↓
DEFEAT_CHECK
↓
TURN_END
↓
NEXT_TURN
```

各イベントで、そのタイミングを発動条件に持つパッシブを確認します。これにより、「攻撃された時」「HPが半分になった時」「味方が倒された時」などを、エンジン本体の大幅な変更なしで追加できる構造にします。

同じ入力を二重処理しないこと、処理途中の例外で中途半端な戦闘状態を保存しないことを必須とします。

## 26. バトル終了

### 26.1 勝敗条件

- 基本勝利：相手の使い魔5体をすべて戦闘不能にする。
- 特殊敗北：自ギルドの持ち時間が0になる。
- 【決定必要】両ギルドが同じ処理内で全滅した場合の引き分け判定。
- 【決定必要】降参機能を用意するか。
- 【決定必要】運営による強制中止機能と、中止時に戦績を付けるか。

### 26.2 自動終了処理

バトル終了時、Botは次を順番に実行します。

1. 勝敗を確定する
2. 結果Embedを投稿する
3. Battleを終了状態へ更新する
4. command操作を停止する
5. 残っているターンメンションを削除する
6. 両ギルド5人全員のセット使い魔を解除する
7. 両ギルドの編成ロックを解除する
8. 出場者専用TCの権限を整理する
9. 一時的な戦闘状態を終了する
10. 戦績と必要なログを保存する

一部のDiscord操作に失敗してもDB上の勝敗確定を繰り返さず、未完了の後片付けだけを再実行できるようにします。

- 【決定必要】勝者・敗者へのcoin、アイテム、経験値などの報酬。
- 【決定必要】ギルド戦績の表示方法とランキング。
- 【決定必要】終了後に出場者専用TCの閲覧権限を外すか、次回編成まで維持するか。

## 27. データベース

最低限、次のテーブルを用意します。

| テーブル | 主な用途 |
| --- | --- |
| `guilds` | ギルド名、マスター、定員、Discordカテゴリー・チャンネルID |
| `guild_members` | プレイヤーと所属ギルド |
| `guild_join_requests` | 未処理・回答済みの参加申請 |
| `familiars` | 使い魔マスターデータ |
| `player_familiars` | プレイヤーが所有する使い魔 |
| `familiar_skills` | アクティブ・パッシブスキル定義 |
| `guild_battle_requests` | 特定ギルドへの対戦申請 |
| `guild_battle_recruitments` | 公開中の対戦募集 |
| `guild_battles` | 対戦ギルド、状態、勝敗、現在ターン、残り時間 |
| `guild_battle_members` | 出場者とセットした所有使い魔 |
| `guild_battle_units` | バトル開始時に作る戦闘用使い魔 |
| `guild_battle_effects` | バフ・デバフ・状態異常 |
| `guild_battle_logs` | 行動、ダメージ、スキル、勝敗の記録 |

- 【決定必要】各テーブルの正式な列、データ型、保存期間。実装前のDB設計で確定します。

必須制約の例：

- 1プレイヤー1ギルドをDBでも保証する
- ギルド内の同一プレイヤー重複を禁止する
- 進行中バトルへ同じギルド・プレイヤーを重複参加させない
- 同じボタン操作や行動IDを二重反映しない
- coin支払いと購入対象の更新を同一トランザクションで行う

既存の `database/core.py` を直接Cogから利用せず、用途別の公開窓口を追加します。

## 28. 実装ファイル構成

現在のRAGNA Botの機能パッケージ構成に合わせ、次を基本とします。

```text
cogs/
├── guild/
│   ├── __init__.py
│   ├── cog.py
│   ├── views.py
│   └── service.py
├── familiar/
│   ├── __init__.py
│   ├── cog.py
│   ├── views.py
│   └── service.py
└── guild_battle/
    ├── __init__.py
    ├── cog.py
    ├── views.py
    └── service.py

database/
├── guild.py
├── familiar.py
└── battle.py

game/
├── __init__.py
├── models.py
├── battle_engine.py
├── skill_engine.py
├── effects.py
└── battle_embed.py
```

責務は次のように分けます。

- `cog.py`：Slash Command、イベント、常設View登録
- `views.py`：ボタン、選択画面、Modal、Embedへの入力受付
- `service.py`：ギルド設立など複数処理をまとめる業務手順
- `database/*.py`：SQLiteの読み書きとトランザクション
- `game/*.py`：Discordに依存しない戦闘計算

## 29. 安全性・運用要件

- すべての操作で、実行者のギルド・役割・現在状態をサーバー側で再確認します。
- ボタンが表示されていても、権限を失ったプレイヤーの操作は拒否します。
- 常設Viewには固定の `custom_id` を付け、Bot再起動後に再登録します。
- coin、所属、勝敗など複数データを更新する操作はDBトランザクションを使用します。
- Discord APIの失敗を想定し、DB更新とチャンネル操作の途中状態を検出・修復できるようにします。
- Railwayの再起動後に、未処理申請、常設パネル、進行中バトルを検査します。
- 進行中バトルのBotは1プロセス・Railway Replica 1台で動かします。
- 管理操作と異常終了はログへ記録します。
- 【決定必要】進行中バトルを再起動後に自動再開するか、運営確認待ちにするか。
- 【決定必要】操作ログに保存するDiscordユーザー情報と保存期間。

### 32.7 運営向け手順

- 問題のあるギルド名を変更・解散させる管理機能
- 固まったバトルを確認・再開・中止する管理機能
- 誤って消えたパネルやチャンネルの復旧手順
- プレイヤー所属と使い魔所有状況の確認手順
- 不正なcoin・戦績を修正する手順
- Railway再起動・DBバックアップ・復元手順
- 障害発生時にユーザーへ案内する定型文

### 32.8 テストデータとテスト参加者

- 最低2ギルド分のテスト用プレイヤー
- 5対5を確認できる最大10人分のテスト構成
- ランクB・A・Sおよび七星のテストケース
- 各ランクのテスト用使い魔
- 残高不足、満員、重複申請、途中脱退などの異常系データ
- 通常攻撃だけで完走するバトルシナリオ
- アクティブ・パッシブを含むバトルシナリオ

実際の10人を常に集めなくても確認できるよう、Battle EngineにはDiscordを使わない自動テストを用意します。

### 32.9 監視・バックアップ

- Railway Volumeの定期バックアップ
- バトル開始・終了・異常停止ログ
- DB整合性と進行中バトルの起動時チェック
- Discord APIエラーと処理再試行の記録
- ギルド数、進行中バトル数、失敗操作数を確認できる運営ログ
- 【決定必要】戦闘ログと戦績の保存期間

### 32.10 公開前チェック

- テストサーバーでギルド機能を一通り操作する
- Railway再起動後に常設パネルと権限が復旧する
- 同時操作やボタン連打で二重課金・二重行動が起きない
- 既存のCoin、評価、宿屋、問い合わせ機能に影響がない
- DBバックアップから復元できる
- ユーザー向け説明と運営手順が完成している
- 未決定事項のうち、公開範囲に必要な項目がすべて解決している
