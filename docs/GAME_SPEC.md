# RAGNA Online ギルド・ギルドバトル仕様書

## 1. この文書について

この文書は、RAGNA Discord Botへ追加するゲーム機能「RAGNA Online」の正式な設計基準です。
元のアイデアメモに含まれていた具体的な数値、画面例、戦闘ルールを残しながら、実装・確認・運用がしやすい形に整理しています。

- 対象範囲：ギルド、使い魔、ギルドバトル
- 対象外：既存の評価、宿屋、問い合わせなどの仕様変更
- 本文の数値と挙動は初期リリース用の正式仕様です。運用後の調整は変更履歴を残して行います。

この文書に書かれていない挙動を実装時の判断だけで決めず、重要な仕様は追記してから実装します。

### 1.1 ユーザーから見た公開予定機能

ここでは、Discordユーザーが最終的に利用できる機能をまとめます。以下は公開予定の機能であり、現時点で利用できる機能ではありません。
現在利用できるBot機能は [機能一覧](FEATURES.md) を参照してください。ゲーム機能は、実装と本番確認が完了したものから同ファイルへ移します。

#### 一般プレイヤー向け

- ギルド紹介チャンネルで募集中のギルドを確認し、参加申請
- 所属ギルドからの脱退
- ガチャを回して使い魔を入手
- 所有している使い魔の一覧・能力・画像の確認
- 同じ使い魔同士の合成によるレベルアップ
- 不要な使い魔の売却
- ギルドバトル出場時の使い魔セット
- 自分のターンでのスキル使用、攻撃、攻撃対象の選択
- 行動結果、現在HP、強化・弱体化、勝敗の確認

#### ギルドマスター向け

- RAGNA内のゲーム通貨（coin）を支払ってギルドを設立
- 参加申請の承認・拒否
- ギルド紹介の公開・停止と説明文の更新
- メンバー追放、マスター譲渡、メンバー枠拡張、ギルド名変更、ギルド解散
- バトル出場メンバー5人の選択と準備状況の確認
- 特定ギルドへの対戦申請
- 公開チャンネルでの対戦相手募集

#### Botが自動で行うこと

- ギルド専用カテゴリー・チャンネルと閲覧権限の作成・更新
- ギルドの満員、所属重複、使い魔所有状況、出場条件の確認
- 参加承認時に、そのプレイヤーが他ギルドへ出している申請を自動取消
- 行動順、ダメージ、スキル効果、持ち時間、勝敗の計算
- 行動ログと現在の戦況の表示
- バトル終了後の使い魔セット解除、権限整理、戦績保存

## 2. 開発方針

ゲーム機能は次の4段階に分けて公開します。

1. ギルド設立・参加・脱退・管理
2. 使い魔の所有・確認・バトル編成
3. 通常攻撃を中心とした基本ギルドバトル
4. アクティブスキル・パッシブスキル

## 4. 既存RAGNA Botとの対応

- Discordサーバー上の「騎士」ロールを、コードでは設定名 `ROLE_MEMBER` で参照しています。
- Discordサーバー上の「七星」ロールを、コードでは設定名 `ROLE_SUB_MANAGER` で参照しています。
- Discordサーバー上の「運営」ロールを、コードでは設定名 `ROLE_MANAGER` で参照しています。
- ギルド料金は既存のcoin残高から支払います。
- 騎士、七星、運営のいずれかのDiscordロールを持つプレイヤーがギルドを設立できます。
- プレイヤーランクの正式な参照元は、各メンバーのDiscordロール情報を保存するDBへ統一します。Discord上の表示だけで判定せず、ゲーム処理ではこのDBを参照します。

## 5. ギルド基本仕様

### 5.1 所属ルール

- 1プレイヤーが同時に所属できるギルドは1つです。
- ギルド設立者は自動的にギルドマスターになります。
- ギルドマスターもギルド人数の1人として数えます。
- 初期定員は5人です。
- メンバー枠は1枠100,000 coinで拡張できます。
- 1ギルドの最大人数は10人です。
- ゲーム仕様上、サーバー全体のギルド数に上限は設けません。ただし、実際にはDiscord側のカテゴリー・チャンネル数などの技術的な上限を超えて作成できません。

### 5.2 ギルド設立

- 設立費用は1,000,000 coinです。
- 既にギルドへ所属しているプレイヤーは設立できません。
- 残高不足の場合、ギルドやDiscordチャンネルは作成しません。
- 残高確認、費用の減算、取引履歴、ギルド登録は可能な限り一体の処理として扱います。
- Discordカテゴリーまたはチャンネルの作成に失敗した場合、途中状態を残さず、支払ったcoinを返金します。
- ギルド名は1文字以上30文字以下です。
- 同名ギルドを許可します。画面やDBではギルド名ではなくギルドIDで識別します。
- 使用禁止の文字・単語・メンション表現は設けません。Botがギルド名を表示するときは、意図しないメンション通知が発生しない設定で送信します。
- ギルドマスターは専用の変更パネルから、50,000 coinを支払ってギルド名を変更できます。
- 名称変更に成功した場合だけ料金を確定し、DB、カテゴリー名、募集Embedなどの表示を新しい名称へ更新します。

### 5.3 ギルド専用カテゴリー

設立時に次のDiscordカテゴリーとチャンネルを自動作成します。

```text
【ギルド名】
├─ ギルドTC
├─ ギルドVC
├─ ギルドマスター専用TC
├─ バトル出場者専用TC
└─ バトル-<バトルID>   ← 対戦成立時に自動生成し、終了後に自動削除
```

各チャンネルの用途は次のとおりです。

| チャンネル | 用途 |
| --- | --- |
| ギルドTC | ギルドメンバーの日常会話 |
| ギルドVC | ギルドメンバーの通話 |
| ギルドマスター専用TC | 参加申請、ギルド管理、バトル管理 |
| バトル出場者専用TC | 出場者への連絡と使い魔セット |
| バトル専用チャンネル | 戦闘中の攻撃・スキル操作、行動ログ、戦況 |

上4つは設立時に作る常設チャンネルです。バトル専用チャンネルは常設せず、
対戦が成立したときに同じカテゴリー内へ自動生成します（34.14節）。

基本権限は次のとおりです。

- ギルドTC・VC：所属メンバーだけが閲覧・利用できます。
- ギルドマスター専用TC：ギルドマスターだけが閲覧・操作できます。
- バトル出場者専用TC：現在セットされている出場者とギルドマスターが閲覧できます。
- バトル専用チャンネル：所属メンバー全員が閲覧できます。投稿はBotだけが行い、
  操作はBotのボタンから行います。
- Botはすべてのチャンネルを閲覧・管理できます。
- 出場者セットを変更した場合、専用TCの閲覧権限を自動更新します。
- 運営ロールを持つメンバーは、すべてのギルドチャンネルを閲覧できます。
- 運営以外のメンバーは、自分が所属するギルドの許可されたチャンネルだけを閲覧できます。
- ギルド解散後、カテゴリーとチャンネルは即時削除せず、一定期間アーカイブします。
- 新しいギルドカテゴリーはDiscordサーバーのカテゴリー一覧の末尾へ作成します。Discordではカテゴリーを別カテゴリーの中へ入れられないため、親カテゴリーは使用しません。
- 解散したギルドカテゴリーは一覧の末尾へ移動し、カテゴリー名の先頭に `【解散済】` を付けて30日間保存します。30日後にDiscord上のカテゴリーとチャンネルを削除します。
- アーカイブ中のカテゴリーは運営だけが閲覧できます。元メンバーを含む一般プレイヤーには公開しません。
- Discord上のカテゴリーを削除した後も、ギルドの基本情報、戦績、バトル結果はDBに残します。詳細な行動ログの保存期間は32.9節に従います。

カテゴリーID、各チャンネルID、作成状態はDBへ保存し、Bot再起動後も利用できるようにします。

## 6. ギルド募集・参加申請

### 6.1 メンバー募集チャンネルでの募集

ギルド紹介チャンネルとメンバー募集チャンネルは別のチャンネルです。用途は次のとおりです。

| チャンネル | 用途 | 環境変数 |
| --- | --- | --- |
| ギルド紹介チャンネル | ギルド設立パネル、自分の参加申請の確認・取消 | `GUILD_INTRO_CHANNEL_ID` |
| メンバー募集チャンネル | 各ギルドの募集Embedと参加申請 | `GUILD_MEMBER_RECRUITMENT_CHANNEL_ID` |

ギルド検索パネルは設置しません。ギルドマスターが募集を開始すると、メンバー募集チャンネルへ募集Embedを投稿し、参加希望者はそのEmbedから申請します。

```text
【ギルドメンバー募集】

ギルド名
VALHALLA

説明
初心者歓迎。夜を中心に活動しています。

メンバー
5 / 10

状態
募集中

[参加申請]
```

- ギルドは所属メンバー、説明文、募集状態を持ちます。
- 募集状態は少なくとも「募集中」と「募集停止」を持ちます。
- ギルドマスターは管理パネルから募集の開始・停止と説明文の変更を行えます。
- 募集開始時はEmbedを新規投稿し、人数・名称・説明文・募集状態が変わった場合は既存Embedを更新します。
- 募集停止後もEmbedは残し、「募集停止」と表示して参加申請ボタンを無効化します。
- 満員のギルドには申請できません。
- 既にギルドへ所属しているプレイヤーは新規申請できません。
- ギルド説明文は1文字以上300文字以下です。募集を開始するには説明文の登録を必須とします。
- 各チャンネルはRailwayの環境変数で指定します。実在する本番チャンネルIDはデプロイ時に設定し、コードやこの文書へ直接書きません。

### 6.2 参加申請

募集Embedの「参加申請」を押すと、対象ギルドのギルドマスター専用TCへ次のようなEmbedを投稿します。

```text
【ギルド参加申請】

申請者
@Player

[承認] [拒否]
```

- 承認すると、申請者をギルドメンバーとして登録し、ギルドチャンネルの権限を付与します。
- 拒否すると、ギルドへの加入は行いません。
- 回答済みの申請Embedは削除します。
- マスター専用TCには原則として未処理の申請だけを残します。
- 承認時にも定員と所属状態を再確認します。
- 承認と拒否のボタンは、対象ギルドの現在のマスターだけが操作できます。
- 承認・拒否の結果は申請者へDMで通知します。
- 参加申請に有効期限は設けません。ギルドマスターが回答するか、申請者が別ギルドへ加入するまで有効です。
- 同じプレイヤーが複数ギルドへ同時に参加申請することを許可します。
- いずれかのギルドで承認された場合、そのプレイヤーが他ギルドへ出している未処理申請をすべて強制取消します。対応する申請Embedも削除または取消済み表示へ更新します。
- 拒否後の再申請に待機時間はありません。同じギルドへすぐに再申請できます。
- 申請者は自分の申請一覧から未処理の参加申請を取り消せます。取消後は対象ギルドの申請Embedを削除または取消済み表示へ更新します。

### 6.3 満員時

申請を作る前に、次を判定します。

```text
現在人数 >= ギルド定員
```

満員なら申請者だけへ次の内容を表示します。

> このギルドは現在満員のため参加申請できません。

この場合、ギルドマスターには通知せず、DBにも有効な申請を作りません。

## 7. 脱退・追放・譲渡・解散

### 7.1 一般メンバーの脱退

- 一般メンバーは、自分のギルドTCに置かれたメンバー用パネルの「ギルド脱退」から自分で脱退できます。
- 脱退するとギルド専用チャンネルの閲覧権限を失います。
- 出場者にセットされていた場合は出場者セットからも解除します。
- バトル進行中の出場者は脱退できません。
- バトル申請中、バトル募集中、編成ロック中のメンバーも脱退できません。
- 脱退後に別ギルドへ加入できるまでの待機時間はありません。

### 7.2 メンバー追放

- ギルドマスターは所属する一般メンバーを追放できます。
- 追放後はギルド専用チャンネルの権限を解除します。
- 出場者にセットされていた場合は出場者セットからも解除します。
- マスター自身は追放対象にできません。
- 追放理由の入力は求めません。
- 追放されたことを対象者へDMで通知します。
- 追放後に同じギルドまたは別ギルドへ再申請するまでの待機時間はありません。

### 7.3 マスター譲渡

- ギルドマスターは所属メンバー1人へマスター権限を譲渡できます。
- 譲渡先は現在そのギルドへ所属しているプレイヤーに限ります。
- 譲渡後、旧マスターは一般メンバーになります。
- ギルドマスター専用TCの閲覧権限を同時に切り替えます。
- マスターは直接脱退できません。譲渡後に一般メンバーとして脱退するか、ギルドを解散します。
- 譲渡先本人の承認は必要としません。ギルドマスターの確認操作だけで譲渡を完了します。

### 7.4 メンバー枠拡張

- 1枠につき100,000 coinを支払います。
- 操作できるのはギルドマスターです。
- 残高不足の場合は拡張しません。
- coin減算と定員更新は一体のDB処理として扱います。
- 拡張費用はギルドマスター個人のcoin残高から支払います。
- ギルド共有資金は作りません。
- 最大定員は10人です。10人に達したギルドはそれ以上拡張できません。

### 7.5 ギルド解散

- ギルドマスターだけが実行できます。
- 誤操作を防ぐ確認画面を表示します。
- バトル進行中は解散できません。
- 所属メンバー全員の所属状態とチャンネル権限を解除します。
- 未処理の参加申請、バトル申請、バトル募集を終了します。
- 設立費用、枠拡張費用、名称変更費用は返金しません。
- ギルドの戦績と過去ログは削除せず保存します。
- Discordカテゴリーとチャンネルは削除せず、アーカイブ状態へ変更します。
- アーカイブ時は新規投稿と操作を停止し、カテゴリー名に解散済みであることが分かる表示を加えます。
- アーカイブ期間と閲覧できる対象は、5.3節の30日保存・運営限定閲覧に従います。

## 8. ギルドマスター用パネル

ギルドマスター専用TCへ、次の2つの常設パネルを置きます。

### 8.1 ギルド管理

```text
[メンバー追放]
[ギルド解散]
[マスター譲渡]
[メンバー枠拡張]
[ギルド名変更]
[ギルド説明変更]
[メンバー募集開始]
[メンバー募集停止]
```

### 8.2 ギルドバトル

```text
[メンバーセット]
[セット確認]
[バトル申請]
[バトル募集]
```

### 8.3 ギルドメンバー用パネル

ギルドTCには、一般メンバーが利用する常設パネルを置きます。

```text
[ギルド情報]
[ギルド脱退]
```

常設ボタンには、Discordがボタンを識別する固定ID（`custom_id`）を設定し、RailwayやBotの再起動後にも操作できるようにします。

## 9. バトル出場者セット

- ギルドマスターが、所属メンバーから最大5人を選択します。
- 正式な5対5バトルを開始するには、両ギルドとも5人必要です。
- 選択されたメンバーには、バトル出場者専用TCの閲覧権限を付与します。
- セットを変更した場合、追加された人へ権限を付与し、外れた人から権限を削除します。
- 同じプレイヤーを重複して選択できません。
- 他ギルドのプレイヤーを選択できません。
- バトルの編成がロックされた後はセットを変更できません。
- 初期リリースでは5人未満のカジュアルバトルを提供しません。将来追加する場合は、正式戦とは別モードとして戦績と報酬を分離します。

## 10. 使い魔

### 10.1 データの分離

使い魔は次の3種類のデータに分けます。

1. 使い魔マスター：名前、ランク、基本HP、基本ATK、SPD、COST、性別、画像、スキル
2. 所有使い魔：所有者、使い魔ID、レベルなどプレイヤー固有の情報
3. 戦闘用使い魔：バトル開始時点の能力値と一時的なHP・効果

バトル中のダメージで所有使い魔の永続データを直接変更しません。

### 10.2 使い魔操作パネル

使い魔関連機能には、次の2つの専用パネルを用意します。

| パネル | ボタン |
| --- | --- |
| ガチャパネル | 単発ガチャ／10連ガチャ／排出使い魔の確認 |
| 使い魔管理パネル | 使い魔一覧／使い魔合成／使い魔売却 |

一覧・合成・売却は操作の入口が近いほど使いやすいため、1枚のパネルへまとめます。

#### ガチャパネル

- プレイヤーがガチャを回して使い魔を入手します。
- 入手した使い魔は所有使い魔としてDBへ保存します。
- 同じ種類の使い魔を既に所有していても、新しい個体として入手できます。
- 使用通貨はcoinで、単発は10,000 coin、10回は100,000 coinです。10回実行に割引はありません。
- 通常枠の排出率はCランク45%、Bランク45%、Aランク9%、Sランク1%です。
- 10回実行の10枠目はBランク以上を保証し、Bランク90%、Aランク9%、Sランク1%で抽選します。
- 初期リリースでは天井、期間限定枠、無料ガチャを設けません。
- 実行前に料金と回数を確認し、coin減算と全抽選結果の保存を1つのDB処理として確定します。途中で失敗した場合はcoinを消費しません。
- 結果は実行者だけに見えるEmbedでまとめて表示します。初期演出はランクごとの色と絵文字のみとし、動画や待ち時間を伴う演出は使用しません。
- 「排出使い魔の確認」から、排出対象の使い魔をランクごとに一覧できます。ランクの排出率と、同じランク内で均等配分したときの1体あたりの排出率、10連の保証枠の確率を表示します。未登録ランクの排出率を寄せている場合は、その旨も表示します。

#### 使い魔一覧（使い魔管理パネル）

- プレイヤーが所有する使い魔を一覧表示します。
- 選択した使い魔について、名前、画像、ランク、レベル、HP、ATK、SPD、COST、性別、スキルを確認できます。
- 同じ種類を複数体所有している場合も、個体ごとに区別して表示します。

#### 合成（使い魔管理パネル）

- 同じ種類の使い魔同士を合成してレベルアップします。
- 合成素材に選んだ使い魔は消費します。
- レベルアップできるのは最大10回で、レベル表記はLv.0～Lv.10です。
- レベルアップによりHP、ATK、SPDが変化します。
- 1回のレベルアップにつき、同じ種類の使い魔を素材として1体消費します。素材のランクとレベルは問いませんが、素材が持つレベルは引き継ぎません。
- Lv.0の基本能力に対し、Lv.1上がるごとに最大HPとATKをそれぞれ5%ずつ加算します。計算式は `基本値 × (1 + 0.05 × レベル)` で、小数は四捨五入します。
- SPDはLv.2、4、6、8、10到達時に1ずつ増加し、最大値は100です。SPDが大きいほど先に行動します。
- 合成対象または素材が編成ロック中・進行中バトルで使用中の場合は合成できません。

#### 売却（使い魔管理パネル）

- プレイヤーは不要な所有使い魔を売却できます。
- 売却した使い魔は所有一覧から除外し、取り消しできません。
- 誤操作防止の確認画面を表示します。
- 売却時はcoinを受け取ります。基準価格はCランク2,000、Bランク5,000、Aランク15,000、Sランク50,000 coinです。
- Lv.1以上の売却額は `ランク別基準価格 × (レベル + 1)` とし、合成に使用した個体数を価格へ反映します。
- 編成ロック中・進行中バトルで使用中の使い魔は売却できません。

使い魔の譲渡機能と、対価を伴わない単純削除機能は設けません。

- 2つのパネルは同じ「使い魔」専用チャンネルへ、ガチャ、管理の順で設置します。チャンネルはRailwayの環境変数 `FAMILIAR_PANEL_CHANNEL_ID` で指定します。

### 10.3 バトル用使い魔セット

- 出場者専用TCから、各出場者が自分の所有使い魔を1体選択します。
- 所有していない使い魔は選択できません。
- 出場者セットから外れた場合、使い魔セットも解除します。
- バトル開始直前に、現在も所有しているか再確認します。
- バトル終了後は、両ギルド5人全員の使い魔セットを自動解除します。
- 次のバトルでは改めて使い魔を選択しなければなりません。

### 10.4 使役可能ランク

通常プレイヤーは、自分のランクより1段階上までの使い魔を使用できます。

| プレイヤーランク | 使用可能な使い魔ランク |
| --- | --- |
| C | C・B |
| B | C・B・A |
| A | C・B・A・S |
| S | C・B・A・S |

七星は特権として、プレイヤーランクに関係なくC～Sのすべてを使用できます。Bランクの七星もSランク使い魔を使用できます。

```text
七星か？
├─ YES → C～Sすべて使用可能
└─ NO  → 自分のランクより1段階上まで
```

- Cランクのプレイヤーは、C・Bランクの使い魔を使用できます。
- すべてのプレイヤーにクラス情報が存在する前提とし、クラス未設定状態は通常のゲーム操作では発生しません。
- 将来、使い魔ランクが追加される可能性があります。ランク順と使役可能範囲を設定データとして管理し、追加時に判定ロジック全体を書き直さずに済む構造にします。

### 10.5 所有・成長

- プレイヤーはガチャから使い魔を入手します。
- 初期配布の使い魔はありません。
- 同じ種類の使い魔を複数体所有できます。
- 所有使い魔の初期レベルはLv.0、上限はLv.10です。
- 同じ種類の使い魔を素材として合成することでレベルアップします。
- レベルアップによるHP、ATK、SPDの変化は10.2節の計算式に従います。
- 使い魔の譲渡はできません。
- 使い魔の売却はできます。
- 売却以外の単純削除機能は設けません。

### 10.6 初期使い魔マスター

正式なキャラクター能力とスキルは[使い魔マスターデータ](FAMILIAR_MASTER.md)で管理します。現時点ではSランク5体、Aランク15体、Bランク20体の合計40体です。以前の仮データ8体は使用しません。

- 同じランク内の使い魔は、ガチャで同じ確率になるよう均等に配分します。
- Cランクは未登録です。追加するまで、Cランク分の排出率はBランクへ加算します（34.2節）。Cランクを追加すると、設定を変えずに本文どおりの確率へ戻ります。
- 性別は神話・伝承上の性別に基づく暫定値を全40体へ登録済みです（34.3節）。運営が変更する場合は[使い魔マスターデータ](FAMILIAR_MASTER.md)と `data/master/familiars.json` を同じ変更として更新します。
- 画像は `assets/familiars/<使い魔ID>.png` へ配置します。正式画像がない個体は共通の仮画像 `assets/familiars/default.png` を表示します。使用する画像は運営が権利を保有するもの、または利用許諾を確認したものに限ります。
- COSTはマスターデータへ保存・表示します。初期の5対5バトルには合計COST制限を設けず、COSTによる編成制限を導入する場合は本仕様を改訂します。

## 11. 編成確認

ギルドマスターは出場者と使い魔のセット状況を確認できます。

```text
【ギルドバトル編成】

① @PlayerA
使い魔：ロキ Lv.0
準備：✅

② @PlayerB
使い魔：フェンリル Lv.2
準備：✅

③ @PlayerC
使い魔：ガルム Lv.4
準備：✅

④ @PlayerD
使い魔：未設定
準備：❌

⑤ @PlayerE
使い魔：ニーズヘッグ Lv.0
準備：✅
```

準備完了となる条件は次の両方です。

1. 出場メンバーに選ばれている
2. 使用する使い魔をセット済み

出場者に選ばれていても、使い魔が未設定なら準備状態は `❌` です。

## 12. 対戦成立方法

### 12.1 特定ギルドへのバトル申請

- ギルドマスターが対戦したいギルドを指定します。
- 相手ギルドのギルドマスター専用TCへ申請を送ります。
- 相手マスターは承認または拒否できます。
- 承認時に両ギルドの準備状況を確認し、問題がなければ対戦を成立させます。
- 回答済みの申請パネルは無効化または削除します。
- バトル申請に有効期限は設けません。承認、拒否、または別バトル成立まで有効です。
- 1ギルドが同時に持てる有効なバトル申請は、送信・受信を合わせて1件だけです。
- 申請後も、バトル開始前チェックによって編成がロックされるまでは出場メンバーと使い魔を変更できます。
- 申請を送ったギルドマスターは、相手が回答する前であれば管理パネルから申請を取り消せます。取消後は相手側の申請パネルを無効化し、双方へ取消結果を表示します。

### 12.2 公開バトル募集

ギルドマスターが「バトル募集」を押すと、ギルドバトル募集チャンネルへ次のようなEmbedを投稿します。

```text
⚔ GUILD BATTLE

「VALHALLA」が対戦ギルドを募集しています。

出場人数：5人
状態：対戦相手募集中

[対戦申請]
```

- 他ギルドのマスターが「対戦申請」から申し込めます。
- 自分のギルドへは申し込めません。
- 募集に有効期限は設けません。募集側のギルドマスターは手動で取り消せます。
- 対戦可能条件を満たした最初の1ギルドから申込みを受けた時点で、対戦相手を確定します。
- 同時に複数の申込みが届いても、DB上で最初に確定した1件だけを成立させ、後続の申込みは受付終了として通知します。
- 対戦成立後は募集を終了し、募集Embedを削除せず「募集終了」へ更新して残します。
- 申込み時点で開始前チェックを通過できないギルドは対戦相手として確定せず、その理由を申込者へ表示します。

## 13. バトル開始前チェック

対戦が承認されても、即座には戦闘を開始しません。両ギルドについて次を最終確認します。

- 出場者がちょうど5人いる
- 5人全員が使い魔をセットしている
- セットした使い魔を現在も所有している
- プレイヤーが使役条件を満たしている
- 出場者が現在も対象ギルドへ所属している
- 出場者が他の進行中バトルへ参加していない
- ギルドが他の進行中バトルへ参加していない
- ギルドと各チャンネルが利用可能な状態である

すべて通過した場合に次を実行します。

1. 両ギルドの編成をロックする
2. Battleデータを作成する
3. 10体の戦闘用使い魔を作成する
4. 両ギルドの募集・他の申請を終了する
5. 最初の行動者を決定する

途中で条件を満たさなくなった場合は、バトルを開始せず、両ギルドへ不足内容を具体的に通知します。

## 14. 戦闘用使い魔データ

戦闘用使い魔には最低限、次を保存します。括弧内はDBで使用する内部名です。

| 内容 | 内部名 |
| --- | --- |
| 戦闘用使い魔を識別するID | `battle_unit_id` |
| 参加しているバトルのID | `battle_id` |
| 所属ギルドのID | `guild_id` |
| 所有プレイヤーのDiscordユーザーID | `player_id` |
| プレイヤーが所有する個体のID | `familiar_instance_id` |
| 使い魔の種類を表すID | `familiar_id` |
| レベル | `level` |
| 最大HP | `max_hp` |
| 戦闘中の現在HP | `current_hp` |
| バトル開始時のATK | `base_atk` |
| 強化・弱体化を反映した現在ATK | `current_atk` |
| 素早さ | `speed` |
| 編成コスト | `cost` |
| 性別 | `gender` |
| スキルごとの使用回数 | `active_skill_uses` |
| 戦闘可能か | `alive` |

必要に応じて、現在の行動不能状態、最後に処理したターン、スキル発動履歴なども持たせます。

- 所有使い魔のHPと戦闘中のHPは完全に分離します。
- バトル開始後に所有使い魔が成長しても、進行中バトルの能力値は変えません。
- バトル開始時のHP、ATK、SPDにランダム補正は加えません。同じ編成と効果なら同じ能力値で開始します。

## 15. 行動順

- 両ギルドの戦闘用使い魔10体を、SPD（内部名 `speed`）が大きい順に並べます。
- 1番から10番まで進行した単位を1ラウンドとし、決着していなければ次のラウンドを同じ手順で開始します。
- 戦闘不能の使い魔は自動スキップします。
- 行動不能の使い魔は自動スキップします。
- 自動スキップではギルド持ち時間を消費しません。
- SPDが同じ使い魔がいる場合、その使い魔同士の順番をラウンド開始時にランダムで決め、そのラウンド中は固定します。
- 将来、SPDや実際の行動順を変化させるスキルを追加できます。

## 16. バトル専用チャンネル

対戦成立時に各ギルドのカテゴリー内へ自動生成する `バトル-<バトルID>` が実際の操作場所です。

- 対戦が成立するまで、このチャンネルは存在しません。
- 自分のギルドの使い魔のターンになると、その使い魔の所有プレイヤーをメンションします。
- 操作できるのは現在の行動者本人です。
- 他の出場者、相手ギルド、第三者による操作は拒否します。

```text
@PlayerA
ロキの行動順です。

[特殊スキル] [攻撃]
```

次のプレイヤーへ移るときは、前回のターン通知メッセージを削除し、新しい行動者をメンションします。バトル専用チャンネルには常に現在の操作対象だけが分かる状態を維持します。

ボタンの二重押しや通信の再送が発生しても、同じ行動を2回処理しないようにします。

## 17. プレイヤーターン

基本的な進行は次のとおりです。

1. ターン開始
2. パッシブスキルのターン開始判定
3. 必要ならアクティブスキルを使用
4. 攻撃を選択
5. 対象を選択
6. ダメージ処理
7. 戦闘不能判定
8. 行動終了
9. 効果の残りターン更新
10. 次の行動者へ移動

アクティブスキルは原則として攻撃前に使用します。基本はスキル使用後に通常攻撃を行いますが、スキルの定義によっては攻撃せずにターンを終了できます。

持ち時間が0になる場合以外にも、プレイヤーが操作しないときに自動攻撃する仕組みを設けます。

- 各ターンの操作開始から3分間操作がなければ自動攻撃します。残り時間はターン通知と戦況Embedへ表示します。
- 自動攻撃は、戦闘可能な敵のうち現在HPが最も低い使い魔を対象にします。同じ現在HPの対象が複数いる場合だけランダムに1体を選びます。
- 自動処理ではアクティブスキルを使用せず、通常攻撃だけを行います。途中まで対象を選んでいても、確定操作が完了していなければ同じ規則で対象を決め直します。

## 18. 戦闘ルール

### 18.1 通常攻撃

- DEFは存在しません。
- 基本ダメージは攻撃者の現在ATKです。
- 現在ATKが8なら8ダメージです。
- ダメージにより戦闘中の現在HP（内部名 `current_hp`）を減らします。
- 戦闘中の現在HPが0以下になった使い魔は戦闘不能です。
- ダメージ計算に使用する現在ATKの最低値は0です。デバフ後の現在ATKが0以下なら通常ダメージは0となり、クリティカルが発生しても0ダメージです。

### 18.2 クリティカル

- 攻撃には10%の確率でクリティカルが発生します。
- クリティカルダメージは通常ダメージの1.5倍です。
- 各攻撃ごとに独立して判定します。
- 発生率はコードへ直接書かず、設定値として管理します。
- 1.5倍した結果に小数が出た場合は四捨五入します。例として9ダメージのクリティカルは14ダメージです。
- 通常攻撃だけでなく、ダメージを与えるスキル攻撃にもクリティカルを許可します。

### 18.3 回復

- 回復スキルは自分または味方を対象にできます。
- 戦闘中の現在HPは最大HP（内部名 `max_hp`）を超えません。
- 戦闘不能の使い魔は、蘇生効果が明示されていない通常回復では対象にできません。

### 18.4 2回攻撃

- `ATK × 2` の一括ダメージではありません。
- 通常の攻撃処理を2回実行します。
- 各攻撃でクリティカルや攻撃連動効果を個別に判定します。
- 1回目の攻撃で対象が戦闘不能になった場合、2回目の攻撃は無効にし、別の対象へ振り替えません。
- 個別に2体の対象を選べることがスキルに明記されている場合は例外です。各攻撃の対象を実行前に選び、1回目の対象が戦闘不能になっても、別に選択した生存対象への2回目は実行します。

### 18.5 戦闘不能と蘇生

- 戦闘中の現在HPが0以下になると戦闘不能になります。
- 戦闘不能になっても、その時点で残っているバフ・デバフ情報は保持します。
- 戦闘不能時に発動する蘇生パッシブを処理してから、ギルド全滅を判定します。
- 蘇生時はスキルに記載されたHPで戦闘可能状態へ戻り、残っているバフ・デバフを引き継ぎます。
- 即時戦闘不能効果でも戦闘不能時パッシブは発動します。ただし「戦闘不能になるダメージ」を条件とする効果は、ダメージを与えない即時戦闘不能では発動しません。

## 19. 特殊スキル

### 19.1 共通データ

スキルは最低限、次の情報を持ちます。括弧内はDBで使用する内部名です。

| 内容 | 内部名 |
| --- | --- |
| スキルを識別するID | `skill_id` |
| 表示名 | `name` |
| ユーザー向け説明 | `description` |
| アクティブ・パッシブの区分 | `skill_type` |
| パッシブの発動タイミング | `trigger` |
| 自分・味方・敵などの対象区分 | `target_type` |
| 同時発動時の優先度 | `priority` |
| 1バトル中の使用・発動上限 | `max_uses_per_battle` |
| 発動条件の配列 | `conditions` |
| 回復・強化・ダメージなどの効果配列 | `effects` |
| 使用可能状態 | `enabled` |
| 定義の版番号 | `version` |

スキル区分（`skill_type`）は、プレイヤーが選んで使う `active` または条件を満たしたとき自動発動する `passive` です。

- `conditions` と `effects` は複数条件・複数効果を表せる配列として保存し、Bot起動時に許可された種類、必須項目、数値範囲を検証します。
- 各効果は最低限 `effect_type`、`value`、`duration_turns`、`chance`、`target_type` を持ちます。使わない項目は `null` とし、意味の異なる値を1つの列へ詰め込みません。
- 既存データとの互換性を確認できるよう、スキル定義には整数の `version` を付けます。進行中バトルは開始時にコピーした定義を使い、途中のマスター変更の影響を受けません。

### 19.2 アクティブスキル

プレイヤーが任意にボタンを押して使用します。候補となる効果は次のとおりです。

- 回復
- 魅了
- 毒
- 石化
- 蘇生
- 状態異常反射
- ATKバフ
- ATKデバフ
- 2回攻撃
- 行動不能
- 状態異常解除
- ACTIVE使用禁止
- 攻撃対象の固定
- 現在ATKの交換

各アクティブスキルの初期使用上限は1バトル1回です。スキルごとの使用回数を戦闘用使い魔に保存します。

- 使い魔1体は最大2個のアクティブスキルを持てます。
- 使用回数はスキル単位で管理し、初期値は各スキルにつき1バトル1回です。スキル定義で別の上限を明示できるようにします。
- 対象を選んだ後も、最終確認前であればキャンセルして行動選択へ戻れます。最終確認後または戦闘状態が更新された後は取り消せません。

### 19.3 パッシブスキル

プレイヤーは操作せず、戦闘処理（Battle Engine）が発動条件を満たしたときに自動処理します。

対応できる効果の例：

- HP50%以下になるとATK+2
- バトル開始時に味方全体ATK+1
- 自分が攻撃を受けたときに発動
- 特定の使い魔と同時出場するとATK+2
- 戦闘不能になる直前に発動
- 常時発動

使用できる発動タイミングは次のとおりです。英字はDBで使用する内部名です。

| 発動タイミング | 内部名 |
| --- | --- |
| バトル開始時 | `battle_start` |
| 各ラウンド開始時 | `round_start` |
| 各使い魔のターン開始時 | `turn_start` |
| プレイヤーが行動を選ぶ直前 | `before_action` |
| 状態異常を受ける直前 | `before_status_apply` |
| 攻撃直前 | `before_attack` |
| 攻撃直後 | `after_attack` |
| ダメージを受けたとき | `on_damage` |
| HPが指定条件を超えたとき | `hp_threshold` |
| ターン終了時 | `turn_end` |
| 戦闘不能になる直前 | `before_defeat` |
| 戦闘不能になったとき | `on_defeat` |
| 各ラウンド終了時 | `round_end` |
| 常時 | `always` |

- 同じイベント中に同じパッシブが無限発動しないよう、発動履歴または回数制限を持たせます。
- 発動したパッシブは行動ログへ記録します。
- 同じパッシブは、同じイベント処理IDに対して1回だけ発動できます。初期値は1ターン1回・1バトル1回とし、継続的な効果や複数回発動を許可する場合だけスキル定義で上限を変更します。
- 複数パッシブは、スキル定義の `priority` が小さい順、発動者のSPDが大きい順、戦闘用使い魔ID、スキルIDの順で解決します。これにより同じ状態から再現可能な順序になります。

## 20. バフ・デバフ・状態異常

- 能力変化は割合ではなく固定値です。
- 例：`ATK +3`、`ATK -2`。
- 同じ効果を重ね掛けできます。
- 残りターン数は、効果を受けている使い魔自身の行動終了時に1減らします。
- 残りターンが0になった効果は解除します。
- 効果ごとに発生元、値、残りターンを保存します。
- 同じスキルから同じ対象へ付与できる同種効果は最大3個まで重複します。ATK補正の合計はバフ側最大+10、デバフ側最大-10です。上限を超える分は切り捨て、現在ATK自体は0未満にしません。
- 行動不能で自動スキップした場合も、その使い魔の行動終了として残りターンを1減らします。
- 毒ダメージは対象自身の行動終了時に適用してから残りターンを1減らします。毒ダメージではクリティカルを判定しません。
- 魅了と石化は状態異常です。ATK低下などの能力値低下は状態異常に含めません。
- 状態異常無効、解除、反射は魅了・石化・毒などを対象とし、能力値変化には作用しません。

## 21. 魅了・性別

人型使い魔には性別情報を設定し、次の内部値を基本とします。

| 意味 | 内部値 |
| --- | --- |
| 男性 | `male` |
| 女性 | `female` |
| 性別なし | `none` |

魅了は「異性の場合のみ行動不能」などの条件判定に利用します。

- 性別が `none` の使い魔は、異性を条件とする魅了を受けません。
- 性別を条件としない行動不能スキルも作成できます。その場合は男性・女性・性別なしのすべてを対象にできます。

## 22. ギルド持ち時間

- 各ギルドはバトル開始時に1時間の持ち時間を持ちます。
- 自ギルドのプレイヤーが操作できる状態の間だけ減少します。
- 相手ギルドのターン中は停止します。
- 行動不能による自動スキップでは消費しません。
- 0になったギルドは時間切れで敗北します。
- 残り時間はDBへ保存し、Discord表示へ反映します。
- BotまたはRailwayの停止中は、両ギルドの持ち時間と1ターンの待機時間を減らしません。復旧と整合性確認が完了した時点から再開します。
- 1操作あたり3分の制限時間を設けます。時間切れでは17節の通常攻撃を自動実行し、ギルド全体の持ち時間も実際に経過した3分だけ減少します。

## 23. 行動ログEmbed

行動ログはEmbed形式で投稿し、行動した使い魔の画像をサムネイル表示します。

通常攻撃の例：

```text
⚔ ロキの攻撃                    [ロキ画像]

使用者
@PlayerA

対象
フェンリル

DAMAGE
8

HP
30 → 22
```

クリティカルの例：

```text
⚡ CRITICAL
12 DAMAGE
```

アクティブスキルの例：

```text
✦ SKILL「魅了」

対象：○○
効果：行動不能
残り：2ターン
```

パッシブスキルの例：

```text
✦ PASSIVE SKILL

ロキ「○○」発動
ATK +2
```

- 行動ログは両ギルドのバトル専用チャンネルへ同じ内容を投稿します。初期リリースでは共通の公開観戦チャンネルを作りません。
- Discord上のログは各ギルドのチャンネル履歴として残し、現在のギルドメンバーと運営が閲覧できます。DB上の詳細な行動ログは365日、勝敗・対戦相手・日時などの戦績概要は無期限で保存します。

## 24. 戦況Embed

各行動終了後に、その時点の戦況をEmbedで表示します。

- 行動ログ：今回何が起きたか
- 戦況Embed：その結果、現在どうなっているか

両ギルド5体について次を表示します。

- 使い魔名
- HPバー
- 現在HP / 最大HP
- 現在ATK
- SPD
- 戦闘不能状態
- バフ
- デバフ
- 状態異常
- アクティブスキル使用状況

- 戦況Embedはチャンネルごとに最新の1件を編集して更新します。対象メッセージが削除されていた場合だけ新規投稿します。
- HPバーは10文字で、残りHPを `█`、失ったHPを `░` で表示します。HPが1以上なら残量部分を最低1文字表示し、戦闘不能時はすべて `░` にします。
- 最大HP、現在HP、現在ATK、SPD、状態効果、使用済みスキルを両ギルドへ公開します。内部ID、乱数値、未発動パッシブの判定情報だけは表示しません。

## 25. 戦闘処理（Battle Engine）

戦闘処理はDiscordのボタンやEmbedから分離し、入力された戦闘状態と行動から次の状態を計算します。

基本イベント順：

```text
BATTLE_START
↓
ROUND_START
↓
TURN_START
↓
BEFORE_ACTION
↓
SKILL
↓
BEFORE_STATUS_APPLY・STATUS_APPLY（状態異常を付与する場合）
↓
BEFORE_ATTACK
↓
ATTACK
↓
DAMAGE
↓
AFTER_ATTACK
↓
BEFORE_DEFEAT（戦闘不能になる場合）
↓
DEFEAT_CHECK
↓
TURN_END
↓
NEXT_TURN
├─ 未行動の使い魔がいる → TURN_START
└─ 全員の行動が完了 → ROUND_END → ROUND_START
```

| イベント | 意味 |
| --- | --- |
| `BATTLE_START` | バトル開始時 |
| `ROUND_START` | 各ラウンド開始時 |
| `TURN_START` | 各使い魔のターン開始時 |
| `BEFORE_ACTION` | プレイヤーが行動を選ぶ直前 |
| `SKILL` | スキル処理中 |
| `BEFORE_STATUS_APPLY` | 状態異常を付与する直前 |
| `STATUS_APPLY` | 状態異常を付与したとき |
| `BEFORE_ATTACK` | 攻撃直前 |
| `ATTACK` | 攻撃実行時 |
| `DAMAGE` | ダメージ反映時 |
| `AFTER_ATTACK` | 攻撃直後 |
| `BEFORE_DEFEAT` | 戦闘不能になる直前 |
| `DEFEAT_CHECK` | 戦闘不能の確認時 |
| `TURN_END` | ターン終了時 |
| `NEXT_TURN` | 次の行動者へ移るとき |
| `ROUND_END` | 各ラウンド終了時 |

各イベントで、そのタイミングを発動条件に持つパッシブを確認します。これにより、「攻撃された時」「HPが半分になった時」「味方が倒された時」などを、エンジン本体の大幅な変更なしで追加できる構造にします。

同じ入力を二重処理しないこと、処理途中の例外で中途半端な戦闘状態を保存しないことを必須とします。

## 26. バトル終了

### 26.1 勝敗条件

- 基本勝利：相手の使い魔5体をすべて戦闘不能にする。
- 特殊敗北：自ギルドの持ち時間が0になる。
- 反動や同時効果により同じイベント処理内で両ギルドが全滅した場合は引き分けとします。
- ギルドマスターは確認画面を経て降参できます。降参したギルドを敗北、相手ギルドを勝利として通常の戦績へ記録します。
- 運営は異常停止や不正対応のためバトルを強制中止できます。強制中止は勝敗なしの `aborted` として保存し、通常の勝敗数、ランキング、報酬には反映しません。中止理由の入力を必須とします。

### 26.2 自動終了処理

バトル終了時、Botは次を順番に実行します。

1. 勝敗を確定する
2. 結果Embedを投稿する
3. DB上の試合状態を「終了」へ更新する
4. バトル専用チャンネルの操作を停止する
5. 残っているターンメンションを削除する
6. 両ギルド5人全員のセット使い魔を解除する
7. 両ギルドの編成ロックを解除する
8. 出場者専用TCの権限を整理する
9. 一時的な戦闘状態を終了する
10. 戦績と必要なログを保存する

一部のDiscord操作に失敗してもDB上の勝敗確定を繰り返さず、未完了の後片付けだけを再実行できるようにします。

- 通常決着では各出場者へ、勝者20,000 coin・100 XP、敗者5,000 coin・25 XP、引き分け10,000 coin・50 XPを付与します。初期リリースではアイテム報酬を設けません。
- 報酬対象は1プレイヤーにつき日本時間の1日3試合までとし、同じ2ギルド間では1日最初の1試合だけを報酬対象にします。戦績自体は上限後も記録します。
- 降参は、第3ラウンドに入る前（第1・第2ラウンド中）に行われた場合、両ギルドとも報酬なしとします。第3ラウンド以降の降参には通常の勝敗報酬を適用します。運営による強制中止では報酬を付与しません。
- ギルドごとに通算の勝・敗・引き分けを表示します。ランキング得点は勝利3点、引き分け1点、敗北0点とし、得点、勝利数、敗北数の少なさ、ギルドIDの順で順位を決めます。ランキング対象は活動中のギルドだけとし、パネルには上位20ギルドと利用者自身の所属ギルド順位を表示します。
- バトル終了後は出場者セットを解除し、一般出場者から出場者専用TCの閲覧権限を外します。ギルドマスターと運営の権限は維持します。

## 27. データベース

最低限、次のテーブルを用意します。

| テーブル | 主な用途 |
| --- | --- |
| `guilds` | ギルド名、説明文、マスター、定員、募集・アーカイブ状態、Discordカテゴリー・チャンネル・募集EmbedのID |
| `guild_members` | プレイヤーと所属ギルド |
| `guild_join_requests` | 未処理・回答済みの参加申請 |
| `player_roles` | プレイヤーのDiscordロールとゲーム内ランクの同期情報 |
| `familiars` | 使い魔マスターデータ |
| `player_familiars` | プレイヤーが所有する使い魔 |
| `familiar_skills` | アクティブ・パッシブスキル定義 |
| `familiar_gacha_pools` | ガチャの種類、料金、公開状態 |
| `familiar_gacha_entries` | ガチャごとの排出対象と確率 |
| `familiar_transactions` | ガチャ入手、合成、売却の履歴 |
| `guild_battle_requests` | 特定ギルドへの対戦申請 |
| `guild_battle_recruitments` | 公開中の対戦募集 |
| `guild_battles` | 対戦ギルド、状態、勝敗、現在ターン、残り時間 |
| `guild_battle_members` | 出場者とセットした所有使い魔 |
| `guild_battle_units` | バトル開始時に作る戦闘用使い魔 |
| `guild_battle_effects` | バフ・デバフ・状態異常 |
| `guild_battle_logs` | 行動、ダメージ、スキル、勝敗の記録 |

- 正式な列、データ型、インデックス、外部キーはルートの `schema.sql` とDBマイグレーションを唯一の正式定義とし、この文書へ重複記載しません。
- 主キーはSQLiteの整数ID、Discordのユーザー・サーバー・チャンネル・メッセージIDは64bit整数、日時はUTCのISO 8601文字列、状態値は制約付き文字列を基本とします。
- 所属、申請、編成、進行中バトルは物理削除せず状態と更新日時を残します。詳細なバトル行動ログは365日、運営操作ログは180日、coin取引、使い魔取引、ギルド戦績、バトル結果概要は無期限で保存します。

必須制約の例：

- 1プレイヤー1ギルドをDBでも保証する
- ギルド内の同一プレイヤー重複を禁止する
- ギルド名は重複を許可し、ギルドIDで識別する
- 参加承認と他ギルドへの申請取消を同一トランザクションで行う
- 1ギルドが持てる有効なバトル申請を1件に制限する
- 進行中バトルへ同じギルド・プレイヤーを重複参加させない
- 同じボタン操作や行動IDを二重反映しない
- coin支払いと購入対象の更新を同一トランザクションで行う

プレイヤーランクは `player_roles` テーブルから取得します。Bot起動時、メンバー参加時、ロール更新時にDiscordの状態を同テーブルへ同期し、ゲーム処理中はDiscord上の表示を直接の正式データにはしません。同期に失敗して情報が確認できない場合は、推測でランクを補わず対象操作を停止して運営ログへ記録します。

既存の `database/core.py` を直接Cogから利用せず、用途別の公開窓口を追加します。

│   └── service.py

責務は次のように分けます。

- `database/*.py`：SQLiteの読み書きとトランザクション
- `game/*.py`：Discordに依存しない戦闘計算

## 29. 安全性・運用要件

- すべての操作で、実行者のギルド・役割・現在状態をサーバー側で再確認します。
- ボタンが表示されていても、権限を失ったプレイヤーの操作は拒否します。
- 常設Viewには固定の `custom_id` を付け、Bot再起動後に再登録します。
- coin、所属、勝敗など複数データを更新する操作はDBトランザクションを使用します。
- Discord APIの失敗を想定し、DB更新とチャンネル操作の途中状態を検出・修復できるようにします。
- Railwayの再起動後に、未処理申請、常設パネル、進行中バトルを検査します。
- 進行中バトルの二重処理を防ぐため、Railway上で同じBotを同時に起動する数（Replica）は1台にします。
- 管理操作と異常終了はログへ記録します。
- 再起動後は進行中バトルのDB整合性、両ギルド、出場者、Discordチャンネルを検査します。問題がなければ停止中の時間を差し引かず自動再開し、問題があれば `paused` 状態にして運営の再開または中止判断を待ちます。
- 運営操作ログには、実行者のDiscordユーザーID、対象ユーザー・ギルド・バトルID、操作種別、成功・失敗、理由、処理ID、UTC日時を保存します。表示名、DM本文、一般チャンネルのメッセージ本文は保存しません。保存期間は180日です。

## 30. 段階別の完成条件

### 30.1 ギルド機能

- 設立、名称変更、専用チャンネル作成が動作する
- ギルド紹介Embedの公開・停止・更新と、そこからの参加申請が動作する
- 参加申請の承認・拒否・DM通知・他申請の自動取消が動作する
- 満員時に申請や通知を作らない
- 脱退、追放、譲渡、最大10人までの枠拡張、解散・アーカイブが動作する
- coinとギルドデータに途中状態を残さない
- Bot再起動後も管理パネルが動作する

### 30.2 使い魔・編成

- ガチャパネルと使い魔管理パネル（一覧・合成・売却）を利用できる
- 同種の複数所有とLv.0～Lv.10の個体を正しく管理できる
- 所有使い魔を確認し、バトル用の1体を選択できる
- ランクと七星特権を正しく判定する
- 出場者5人と使い魔5体の準備状態を確認できる
- 出場者専用TCの権限が編成と一致する

### 30.3 基本バトル

## 34. 実装時に確定した補足仕様

本文だけでは挙動が一意に決まらなかった点を、実装と同時に確定した内容です。
1節の方針に従い、実装側の判断で暗黙に決めず、ここへ明記します。

### 34.1 段階公開のスイッチ

- 環境変数 `GAME_ENABLED` が真のときだけ、ゲームの常設パネルを設置します。
  偽の間もCogは読み込み、DBとマスターデータの整合性確認は実行します。
- マスターデータの読み込みに失敗した場合、ゲーム機能の3つのCogだけを読み込まず、
  既存機能（coin、評価、宿屋、問い合わせなど）は通常どおり起動します。

### 34.2 Cランク未登録時のガチャ

10.6節のとおり、Cランクのマスターデータは未登録です。実装では次のように扱います。

- 使い魔が1体も登録されていないランクは抽選対象から除外します。
- 除外したランクの確率は、`data/master/gacha.json` の `missing_rank_fallback` で
  指定したランクへまとめて加算します。現在の設定はBランクです。
  例：通常枠のCランク45%を除外すると、B90%・A9%・S1%になります。
- 10回実行の10枠目（保証枠）はCランクを含まないため、本文どおりB90%・A9%・S1%のままです。
- 加算が発生した回は、ガチャ結果Embedへ調整している旨と加算先を明記します。
- Cランクのマスターデータを追加すると、設定を変更せずに本文どおりの確率へ戻ります。
- `missing_rank_fallback` が未設定、または寄せ先のランクも未登録の場合は、
  残るランクへ元の比率のまま按分します。

### 34.3 性別の登録方針

- 使い魔マスターの性別は「男性（`male`）」「女性（`female`）」「性別なし（`none`）」です。
  未登録（`null`）も表現できますが、現在は全40体へ登録済みです。
- 登録値は神話・伝承上の性別に基づく暫定値です。人型でない個体や、
  伝承上で性別が定まらない個体は「性別なし」としています。
- 「性別なし」と「未登録」は、どちらも異性を条件とする効果の対象にも発動元にもなりません。
- 運営が性別を見直す場合は、`data/master/familiars.json` と
  [使い魔マスターデータ](FAMILIAR_MASTER.md)の性別欄を同じ変更として更新します。

### 34.4 現在ATKの交換（虚実反転）

- 交換時点の現在ATKを互いの基準値として保存します。
- 交換後に受けたバフ・デバフは、この基準値へ加算します。
- ラウンド終了時に交換を解除し、元の基準値へ戻します。

### 34.5 効果の残りターンと自分のターン

- 20節の「効果を受けている使い魔自身の行動終了時に1減らす」を基本としますが、
  その使い魔自身のターン中に付与された効果は、同じターンでは減らしません。
- これにより「味方1体の状態異常を解除し、次の自身の行動終了まで新たな状態異常を
  受けない」を自分自身へ使った場合も、1ターン分の効果が有効になります。

### 34.6 対戦申請・募集・進行中バトルの排他

- 12.1節の「有効なバトル申請は送信・受信を合わせて1件だけ」を、DB上の
  ギルド単位のロックで実現します。ロックは申請・募集・進行中バトルで共用します。
- そのため、1ギルドは「申請中」「募集中」「バトル中」のいずれか1つの状態しか
  同時に持てません。取消・拒否・バトル終了でロックを解放します。

### 34.7 ギルド専用チャンネルの権限

- ギルドごとのDiscordロールは作成せず、メンバー個別の権限上書きで制御します。
- 1ギルドの最大人数は10人のため、Discordの権限上書き数の上限には達しません。
- 所属や出場者が変わるたびに、対象チャンネルの権限を作り直して同期します。

### 34.8 スキル定義の対象選択

- アクティブスキルは、対象選択の要求を「選択グループ」の配列として持ちます。
  各グループは対象の陣営（敵・味方）、選択数、絞り込み条件を持ちます。
- 「虚実反転」は敵1体と味方1体の2グループ、「終末の進軍」は敵2体を
  同じ対象で重複選択できる1グループとして定義します。
- 効果は選択グループのキーを参照して対象を決めます。

### 34.9 メンバー追放と編成ロック

- 9節は「編成がロックされた後はセットを変更できません」と定めています。
  メンバー追放も出場者セットからの除外を伴うため、7.1節の脱退と同じく、
  編成ロック中とバトル進行中は実行できません。
- 一方、7.5節が定めるとおり、解散はバトル進行中だけを拒否します。
  未処理のバトル申請・バトル募集は解散処理の中で終了させます。

### 34.10 設立時の参加申請の扱い

- 6.2節は参加申請を「申請者が別ギルドへ加入するまで有効」と定めています。
  ギルド設立は自分のギルドへの加入にあたるため、設立が確定した時点で、
  その設立者が他ギルドへ出している未処理の参加申請をすべて取り消します。
- 取消は設立と同じトランザクションで行い、対応する申請Embedも削除します。

### 34.11 運営によるバトルの再開・中止

26.1節の強制中止と、29節の「運営の再開または中止判断」を次のSlash Commandで行います。
どちらも運営ロールを持つメンバーだけが実行でき、結果を運営ログへ記録します。

| コマンド | 用途 |
| --- | --- |
| `/バトル中止` | 勝敗なしの `aborted` として終了する。中止理由の入力は必須 |
| `/バトル再開` | 一時停止（`paused`）中のバトルを再点検して再開する |

- 強制中止では報酬を付与せず、通算の勝敗数・ランキングにも反映しません。
- 中止・再開のいずれでも、編成ロック、対戦の占有ロック、出場者セット、
  使い魔の使用中状態を必ず解除します。これらが残ると、両ギルドが以後の
  バトルも使い魔の合成・売却もできなくなるためです。

### 34.12 出場者セットの解除範囲

- 26.2節の「バトル終了後は出場者セットを解除し」に従い、バトル終了時は
  使い魔のセットだけでなく、出場者5人の選択そのものを解除します。
- 選択を残すと、その後にメンバーが増減したときの権限再計算で、
  出場者専用TCの閲覧権限が元出場者へ復活してしまいます。

### 34.13 使い魔画像が無い場合

- 使い魔画像は `assets/familiars/<使い魔ID>.png` に置きます。
- 該当ファイルが無い個体は、共通の仮画像 `assets/familiars/default.png` を表示します。
- 仮画像も無い場合は、サムネイルなしでEmbedだけを表示し、処理は止めません。
- 仮画像は `python scripts/make_familiar_placeholder.py` で再生成できます。

### 34.14 バトル専用チャンネル

5.3節のとおり、バトル用チャンネルは常設しません。

- 対戦が成立した時点で、両ギルドのカテゴリー内へ `バトル-<バトルID>` を自動生成します。
- 所属メンバー全員が閲覧できます。投稿はBotだけが行い、操作はBotのボタンから行います。
- 行動ログ、戦況Embed、ターン通知、結果Embedはこのチャンネルへ投稿します。
- バトル終了後もしばらく記録として残し、`battle_channel_retention_days`
  （既定7日）を過ぎたら自動削除します。
- 生成に失敗した場合はバトルを開始しません。再起動後の点検でも、
  このチャンネルが見つからないバトルは `paused` にして運営の判断を待ちます。

### 34.15 Discord APIの一時的な失敗の扱い

- 募集Embedなど、DBにメッセージIDを保存している表示は、
  「利用者が削除した」場合だけ記録を消し、次回に新規投稿します。
- Discord側の一時的な失敗（レート制限、5xx、権限の一時的な不足）では
  記録を消しません。記録を消すと同じ募集Embedが二重に投稿されるためです。
- ギルド設立でチャンネル作成に失敗した場合は、例外の種類を問わず
  作成済みチャンネルを削除し、設立費用を全額返金します（5.2節）。
- ギルド解散では、カテゴリーのアーカイブとは別に、
  専用チャンネルの閲覧権限の解除を独立して実行します。アーカイブに失敗しても
  元メンバーが閲覧できる状態を残さないためです（5.3節・7.5節）。
